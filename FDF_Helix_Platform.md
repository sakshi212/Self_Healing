## Page 10 — Helix Porter User Guide

*Last updated: 2026-06-24 by Thejesh Chandar Rao*

### Overview

Helix Porter is a migration tool that converts workflow configurations from **CDF** (Config Driven Framework) and **IDF** (Intelligent Data Foundation) formats to the **AEOLUS platform** format. Runs locally on your system.

### Tech / Frameworks Covered

| Tech / Framework | Teams Covered | Status |
|-----------------|---------------|--------|
| CDF | International Data Foundations / Sams Foundation (partial) | ✅ Ready — converted pipelines deployed in prod |
| IDF | SAP / IBG / FCP / ICP | ✅ Ready — converted pipelines deployed in prod |
| Spark Scala (FDL) | Sams Foundations / US Sales / US Wages / US Receipts / US SAP | ✅ Ready — teams already using |
| Scheduler Config Creation | All teams | ✅ Ready — teams already using |
| Spark Functional (FDP) | FDP | 🔄 Ready for domain team trials |
| Archetype | FDF Digital Foundation | ✅ Ready — teams already using |
| UDP Workbench | FDP and other teams | 🔄 Ready for domain team trials |
| SQL | | ✅ Ready — teams already using |

### Prerequisites

- Membership in AD group: **`gcp-fdf-helix-porter-reader`**
- Python version 3.12
- Git access to relevant repositories
- [gcloud CLI](https://cloud.google.com/sdk/docs/install) installed and configured

### Installation

**1. Set up Python virtual environment:**
```bash
python3 -m venv helix-porter-env
source helix-porter-env/bin/activate
```

**2. Configure pip to use Walmart's internal artifact repository:**
```bash
pip3 config set global.trusted-host "pypi.ci.artifacts.walmart.com"
pip3 config set global.index-url "https://pypi.ci.artifacts.walmart.com/artifactory/api/pypi/public-cloud-pypi/simple"
```

**3. Install the package:**
```bash
pip3 install -U https://pypi.ci.artifacts.walmart.com/artifactory/api/pypi/fdlhdomains-pypi-prod-local/walmart-finance-datalakehouse-helixporter/0.3.1/walmart-finance-datalakehouse-helixporter-0.3.1.tar.gz
```

**4. Authenticate with Google Cloud:**
```bash
gcloud auth application-default login
```

### Configuration Guide

**Step 1 — Initialize based on source framework:**

```bash
# CDF workflows
helix init --source=cdf

# IDF workflows
helix init --source=idf

# Spark Scala (UDP CLI)
helix init --source=udp_cli

# FDP Team workflows
helix init --source=fdp_scala

# Archetype Team
helix init --source=archetype

# SQL
helix init --source=sql

# Scheduler config creation (launches web UI at http://localhost:8501)
helix scheduler
```

**Step 2 — Repository configuration**

Repository URLs support both HTTPS and SSH:

| Format | Example | Authentication |
|--------|---------|----------------|
| HTTPS | `https://gecgithub01.walmart.com/DPA/repo.git` | Git credentials / credential manager |
| SSH | `git@gecgithub01.walmart.com:DPA/repo.git` | SSH keys |

Configure your `migrate.yaml` based on your source framework. See Confluence page for YAML examples per framework type.

**UDP Workbench SSL prerequisite:**
```bash
# Step 1: Export Walmart cert chain
openssl s_client -connect udp-api.us.walmart.net:443 -showcerts < /dev/null 2>/dev/null \
  | sed -n '/-----BEGIN CERTIFICATE-----/,/-----END CERTIFICATE-----/p' > walmart_cert_chain.pem

# Step 2: Combine with system certs
cat /opt/homebrew/etc/ca-certificates/cert.pem walmart_cert_chain.pem > combined_certs.pem

# Step 3: Set env vars (update paths for your machine)
export SSL_CERT_FILE="/path/to/combined_certs.pem"
export REQUESTS_CA_BUNDLE="/path/to/combined_certs.pem"
export CURL_CA_BUNDLE="/path/to/combined_certs.pem"
```

**Step 3 — Migration settings**

| Setting | Option | Description |
|---------|--------|-------------|
| `conversion_strategy` | `skip` | Skip existing files in output directory |
| `conversion_strategy` | `overwrite` | Always convert and replace existing files |
| `output_target` | `local` | Save files to local filesystem |

**Step 4 — Run migration:**
```bash
helix migrate
```
Check the `output` directory for converted workflow files.

## Page 15 — Helix DOP Integration

*Last updated: 2026-06-09 by Suman Mondal*

### Executive Summary

The **DOP (Deployment Operations Platform) Integration** automates Astronomer namespace onboarding for FDLH domain teams. After every successful deployment (K8s or Celery), the Helix pipeline calls the DOP API to register the Astronomer namespace against the team's TR Product ID.

**Key capabilities:**
- **Fully Automated** — DOP onboarding triggers automatically post-deployment, zero manual steps
- **Multi-Tenant Support** — Handles K8s and Celery tenants independently
- **Non-Blocking** — DOP failures are logged but never block the deployment pipeline
- **Environment-Aware** — Separate API endpoints and PingFederate URLs for nonprod vs prod
- **Self-Provisioning** — Domain teams configure only `ASTRO_NAMESPACE` in `.concord.yml`

### Authentication — PingFederate ROPC

| Environment | PingFederate URL |
|-------------|-----------------|
| Non-Prod (dev, qa) | `https://pfedcert.wal-mart.com/as/token.oauth2` |
| Prod (preprod, prod) | `https://pfedprod.wal-mart.com/as/token.oauth2` |

**Credential storage:**

| Secret | Source |
|--------|--------|
| `dop-pingfed-ropc-client-id` | Concord Crypto Store (org: `FDLH`) |
| `dop-pingfed-ropc-password` | Concord Crypto Store (org: `FDLH`) |

> Credentials are fetched lazily at runtime via `crypto.exportAsString('FDLH', ...)` — not stored in pipeline variables at startup.

### DOP API Endpoints

| Environment | Base URL |
|-------------|----------|
| Non-Prod | `https://dop.api.dev.walmart.com` |
| Prod | `https://dop.api.prod.walmart.com` |

**Request fields:**

| Field | Description | Example |
|-------|-------------|---------|
| `trProductId` | TR Product ID from domain configuration | `6210` |
| `astronomerNamespace` | Astronomer cluster namespace identifier | `astro-prod-bright-perigee-9890` |

**Response:** HTTP 200/201 = success. Non-2xx = logged as warning, deployment continues.

### Domain Configuration

Domain teams enable DOP by adding to `.concord.yml`:

| Variable | Scope | Description |
|----------|-------|-------------|
| `productId` | Global | TR Product ID (e.g., `6210`) |
| `ASTRO_NAMESPACE` | Per-environment or per-tenant | Primary Astronomer namespace |
| `ASTRO_CELERY_NAMESPACE` | Per-environment or per-tenant (optional) | Celery-specific namespace (falls back to `ASTRO_NAMESPACE`) |

**Guard behavior:** If `ASTRO_NAMESPACE` or `productId` is missing/empty, the DOP step is **safely skipped** with a log message — no error raised.

### Error Handling

| Scenario | Pipeline Impact |
|----------|----------------|
| Missing credentials | None — DOP step skipped with warning |
| PingFederate auth failure | None — deployment continues |
| DOP API non-2xx | None — error logged, deployment continues |
| DOP API timeout | None — `ignoreErrors: true` |
| Missing `ASTRO_NAMESPACE` | None — DOP step skipped |

> **Design Principle:** DOP onboarding is **strictly non-blocking**. A DOP failure must NEVER cause a deployment to fail.

### Celery Namespace Resolution Priority

1. Tenant-specific `ASTRO_CELERY_NAMESPACE`
2. Tenant-specific `ASTRO_NAMESPACE`
3. Environment-level `ASTRO_CELERY_NAMESPACE`
4. Environment-level `ASTRO_NAMESPACE`

### Source Location in `fdlh-deploy/concord.yml`

| Component | Lines |
|-----------|-------|
| Global URL variables | 29–32 |
| K8s DOP iterator | 3078–3101 |
| DOP onboarding flow | 3103–3265 |
| Domain namespace config | `<domain>/.concord.yml` per-environment blocks |

### Onboarding Checklist for New Domains

| Step | Action |
|------|--------|
| 1 | Request Astronomer namespace from Platform team |
| 2 | Add `ASTRO_NAMESPACE` to `.concord.yml` per-environment config |
| 3 | (Optional) Add `ASTRO_CELERY_NAMESPACE` if using Celery executor |
| 4 | Ensure `productId` is set in global arguments |
| 5 | Deploy — DOP onboarding triggers automatically |
| 6 | Verify in Concord logs: look for `DOP SUCCESS` messages |

> **No Platform Changes Needed:** DOP integration logic lives entirely in `fdlh-deploy`. Domain teams only add namespace variables — no flow modifications required.

### Timeline

| Date | Milestone |
|------|-----------|

## Page 18 — Automic to Helix Migration

*Last updated: 2026-01-23 by Keerthipriyan Sakthivel*

### Migration Driver

Starting **February 2026**, Automic transitions from **instance-based** to **job-based** billing. Projected cost increase for FDF teams: **~$130K/month**. Migration to Helix (Airflow + Dataproc) is required to avoid this cost escalation.

### Migration Phases

| Phase | Objective | Key Success Criteria |
|-------|-----------|---------------------|
| **Phase 0 — Assessment & Foundation** | Governance, inventory, environment setup | Job catalog, dependency graphs, Airflow dev/test/prod ready, CI/CD pipelines active |
| **Phase 1 — Pilot Migration** | 5–10 low-complexity jobs | Working DAGs aligned with standards, Dataproc ephemeral clusters validated, CI/CD workflow verified |
| **Phase 2 — Core Pipeline Migration** | 60–70% of jobs | Medium-complexity workloads migrated, BQ SQL transformations, DQ checks, regression tests |
| **Phase 3 — Complex / Critical Workloads** | All critical jobs | External connectors, fan-in/out DAGs, error handling, performance optimization |
| **Phase 4 — Cutover & Decommission** | Parallel run → switch → decommission | Output equivalence validated, UAT signoff, Automic jobs disabled |
| **Phase 5 — Optimization & Expansion** | Performance tuning, self-service | FinOps dashboards, full lineage, self-service DAG templates |

### RACI Matrix

**Phase 0 — Migration Planning**

| Activity | Platform Team | Domain Team |
|----------|--------------|-------------|
| Identify jobs/pipelines in scope | C | R / A |
| Define migration timelines | Both team alignment | |
| Provide migration guidelines/utilities | R / A | I |

**Phase 1 — Job Migration & Conversion**

| Activity | Platform Team | Domain Team |
|----------|--------------|-------------|
| Convert Automic jobs to Helix (utility-driven) | R / A | I |
| Validate conversion completeness | R | C |
| Perform sample testing (technical sanity) | R | C |

**Phase 2 — End-to-End Functional Testing**

| Activity | Platform Team | Domain Team |
|----------|--------------|-------------|
| Build functional test cases | I | R / A |
| Execute full regression tests | I | R / A |
| Validate business logic & results | I | R / A |
| Sign-off for migration readiness | I | A |

**Phase 3 — Parallel Run**

| Activity | Platform Team | Domain Team |
|----------|--------------|-------------|
| Support setup for parallel run | R | C |
| Execute and monitor parallel run | C | R / A |
| Compare results & identify discrepancies | C | R / A |

**Phase 4 — Cutover & Production Deployment**

| Activity | Platform Team | Domain Team |
|----------|--------------|-------------|
| Deploy migrated jobs | R / A | I |
| Validate production execution | C | R / A |
| Report issues & remediation | C | R / A |

**Phase 5 — Post-Migration Support**

| Activity | Platform Team | Domain Team |
|----------|--------------|-------------|
| Platform-level issue resolution | R / A | C |
| Functional / business issue resolution | I | R / A |
| Final sign-off | I | A |

### Key Activity Details

**Phase 0 highlights:**
- Airflow deployment model decision: Celery vs K8s executor
- Trunk-based branching strategy (preferred)
- Platform provides naming standards and YAML templates
- Domain teams manage DDL/DML files; Platform provides patterns
- Evaluate schema governance and data contracts strategy

**Phase 1 highlights:**
- Migration utility expected to convert **90%** of pipelines automatically
- Secrets stored in GCP/Helix (not in pipeline variables)
- Keep existing Spark wrappers for compatibility (note library version dependencies)
- Validate Dataproc ephemeral cluster creation for each Spark job type

**Phase 4 key validations:**
- Parallel Automic vs Airflow execution with matching output comparison
- Validate job triggers, DAG defaults, dataset equivalence
- Downstream consumer UAT signoff required before cutover

## Page 20 — Helix Quanta Integration

*Last updated: 2026-08-05 by Harish Kumar Alluri Vinod*

**Execution Model:** Serverless Spark on WCNP Kubernetes
**Job Types:** PySpark, Aeolus, Spark, Spark SQL
**Domains Live:** Cash, Blackline
**Primary Driver:** Cloud compute cost optimization

### What is Quanta?

Quanta is a **GTP-managed, serverless Apache Spark platform** built on WCNP Kubernetes clusters on GCP. Teams submit Spark workloads directly — without provisioning, sizing, or managing clusters.

| Capability | Detail |
|-----------|--------|
| Serverless | No cluster lifecycle to manage |
| Multi-region | `us-west1`, `us-central1`, `us-east4` |
| Multi-tenant | Dedicated RBAC, quotas, workload identity per namespace |
| Compliance | Sensitive, Highly Sensitive, PII, SOX, HIPAA supported |
| Observability | Logs, metrics, Spark UI, History Server, job-level cost attribution |

**Quanta docs:** https://dx.walmart.com/quanta/documentation/confluence/Quanta-Introduction

### Why Quanta?

| Driver | Details |
|--------|---------|
| **Cost reduction** | Dataproc licensing costs eliminated — Quanta runs on open-source Apache Spark |
| **No cluster overhead** | Dataproc needs dedicated cluster provisioning per run (adds minutes). Quanta is serverless |
| **Better utilization** | K8s bin-packing improves node utilization vs dedicated VM-based clusters |
| **Reduced vendor dependency** | Running on WCNP reduces single cloud vendor dependency |
| **Simplified operations** | No cluster sizing, autoscaling, or image version management |
| **Cost transparency** | Job-level chargeback for accurate per-tenant attribution |

### Quanta Submit Operator (Helix)

The same operator as the Dataproc submit operator. Supported job types:

| Job Type | Description |
|----------|-------------|
| `aeolus_job` | Submits Aeolus ETL pipeline — config resolution, variable substitution handled automatically |
| `pyspark_job` | Standard Python/PySpark job |
| `spark_job` | JVM-based Spark job (Java or Scala) with main class entrypoint |
| `spark_sql_job` | Executes SQL from file or inline SQL with runtime variable substitution |

> Since Quanta is serverless, resource sizing (executor/driver memory, cores, instances) is **specified explicitly per job** — not inherited from a cluster shape.

### Domain Team Status

| Domain | Env | Status | Workflows |
|--------|-----|--------|-----------|
| **Cash** | dev | 🟢 LIVE | 7 workflows: PAID_OUT, STORE_INDIV_PCKUP, CASH_REG_DAY, STORE_FIN_ACTV, EXTERNAL_VAULT, DEPOSIT, RECYCLER |
| **Blackline** | dev | 🟢 LIVE | 3 workflows: BLACKLINE_JRNL_LINE_DTL, BLACKLINE_JRNL_HDR_DTL, BLACKLINE_CANADA_DEPOS_UNIFIED_MATCH |

### Migration Plan

| Phase | Description |
|-------|-------------|
| Current | Converted workflows run on Quanta in dev alongside existing Dataproc workflows — capturing Spark runtime and cost metrics for comparison |
| Production rollout | Quanta jobs run in parallel with Dataproc in prod, writing to separate staging tables |
| Parallel monitoring | Both flows monitored side-by-side for 2 weeks — validating data quality, runtime, and cost |
| Decommission | After successful parallel monitoring, Dataproc workflows decommissioned — Quanta becomes primary |

### Challenges & Resolutions During Onboarding

| Issue | Fix |
|-------|-----|
| 401 error on job submission — Cash SA had no roles on tenant `ebstenant001` | Granted Cash SA (`fdlhcashdev-dev-sa1@...`) access; corrected tenant to `fdlhcashdev` |
| Inconsistent `tenant_id` / `quanta_conn_id` naming | Standardized on `tenant_id: fdlhcashdev` and `quanta_conn_id: quanta_conn_id` |
| `conda_env_name: fdlh_env` invalid on Quanta | Dropped `conda_env_name` — runtime provided by Quanta/Aeolus container image |
